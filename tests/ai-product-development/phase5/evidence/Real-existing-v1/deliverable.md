# 反馈整理工具：可执行修改方案

## 1. 现状判断

交付目标：`PARTIAL_PROJECT`，面向现有本地 Golden MVP 的方案设计与实施拆解；本轮不改代码、不扩展云端或多人协作。

已被现有资产证明的能力：

- 支持 CSV 输入；JSON 输入要求为数组。
- 按文本去重。
- 输出 JSON 和 Markdown。
- 支持 `--source` 做来源筛选。
- 主题、情绪、紧急程度均为本地确定性规则，不依赖网络或密钥。
- Markdown 保留原始反馈文本，主题汇总保留反馈 ID。

关键缺口：

1. 分类规则不区分来源。`support`、`interview`、`survey` 当前使用同一套主题和紧急程度词典，无法表达“不同来源有不同判断标准”。
2. 来源筛选不是来源感知分类。`--source support` 只减少输入范围，不改变分类逻辑，也不会输出来源维度的对比结果。
3. 证据引用不完整。当前主要保留 ID 和原文；去重后重复项只进入 `duplicates` 映射，主题证据可能丢失重复反馈来源。样例中 F2 被归为 F1 的重复，最终主题证据只会引用 F1。
4. “证据链接”尚未实现。样例 F5 的文本提到 evidence links，但输入字段和输出结构没有 URL、位置或外部证据引用字段。
5. 主题采用首次命中的单一主题。一个反馈同时涉及性能和可靠性时，只保留第一个匹配结果，存在信息损失。
6. 紧急程度只有 `high/normal`，且只由固定词触发；没有来源规则、冲突处理、原因说明或人工覆盖。
7. README 声称支持 JSON/Markdown 输出，但当前实现要求同时提供 `--json-output` 和 `--markdown-output`，且未说明 JSON 输入字段规范。

## 2. 产品/AI Capability 决策

### 产品能力

建议新增“来源感知的反馈判定”能力：

- 以 `source` 选择对应的主题词典、紧急程度规则和优先级权重。
- 输出每条反馈的：
  - `source`
  - `themes`：允许多个主题
  - `urgency`
  - `classification_reasons`
  - `evidence`
- 汇总按“来源 × 主题”组织，同时保留跨来源总览。
- 去重后保留所有原始反馈作为证据成员，不让重复归并造成证据丢失。
- 支持结构化证据字段，例如 `evidence_url`、`evidence_ref`、`source_item_id`；缺失时明确标记，而不是生成虚假链接。

### AI 边界

当前没有必要引入真实模型、Agent、RAG 或外部服务：

- 现有工具是离线确定性 MVP，业务需求可先由可配置规则满足。
- 规则的可解释性、可复现性和本地运行约束更重要。
- 若后续规则覆盖不足，再以真实样本评测 AI 分类可行性；不能因“主题判断”本身直接升级为模型方案。

## 3. 建议方案

### 输入合同

兼容现有字段，并扩展可选字段：

```text
id, source, text, evidence_url, evidence_ref
```

JSON 继续支持数组，每个对象至少需要 `text`；`id`、`source`、证据字段可选。

规则配置建议先内置在代码中，避免新增配置服务：

```text
source_rules:
  support:
    themes: ...
    urgency: ...
  interview:
    themes: ...
    urgency: ...
  survey:
    themes: ...
    urgency: ...
  default:
    themes: ...
    urgency: ...
```

未配置来源使用 `default`，并在输出中标记 `rule_profile: default`。

### 分类输出

每条反馈至少增加：

```text
themes: ["reliability", "performance"]
urgency: "high"
classification_reasons:
  - "source=support"
  - "matched=crash"
evidence:
  id: "F1"
  text: "原始反馈文本"
  url: null
  ref: null
```

紧急程度规则应明确：

- 来源优先级高于通用默认规则。
- 多条规则命中时取最高等级。
- 无命中时输出 `normal`，并记录未命中原因。
- 不输出未经校准的概率或置信分数。

### 去重与证据

保留现有去重能力，但将重复反馈变为证据集合：

```text
canonical_id: F1
evidence_ids: [F1, F2]
evidence_items: [原始 F1, 原始 F2]
duplicate_of: F1
```

主题汇总的 `evidence` 应包含所有相关原始 ID，而不是只包含 canonical item。

### 输出兼容

- 保留现有 JSON/Markdown 输出参数和字段。
- 旧字段继续存在：`theme` 可暂时保留为主主题，新增 `themes`。
- Markdown 增加来源列、紧急程度、判定原因和证据引用。
- 若无 URL，显示原始 ID/引用，不伪造可点击链接。

## 4. 最小实施顺序与依赖

| 顺序 | 任务 | 主要产物 | 依赖 |
|---|---|---|---|
| P0 | 确认来源规则与标签定义 | 来源规则表、主题/紧急程度枚举 | 业务 owner 确认 |
| P0 | 明确证据字段与去重保留策略 | 输入/输出字段合同 | P0 规则确认 |
| P1 | 改造输入解析与来源规则分派 | CSV/JSON 兼容解析、默认规则 | 上述合同 |
| P1 | 改造分类结果结构 | 多主题、紧急程度、原因 | 来源规则 |
| P1 | 改造去重与证据聚合 | 完整 evidence 集合 | 证据合同 |
| P2 | 更新 JSON/Markdown 渲染 | 兼容输出与来源维度报告 | 分类结果结构 |
| P2 | 建立评测样例与回归集 | 按来源切片的验收数据 | 规则表、输出合同 |

不建议拆出配置服务、数据库、云端存储或多人协作任务；当前没有相应业务触发条件。

## 5. 验收与 Gate 条件

### Qualification Gate

建议：`PASS_WITH_ASSUMPTIONS`

依据：

- 修改范围、现有资产和离线约束明确。
- 尚缺业务确认：每个来源的主题定义、紧急程度规则和证据字段语义。
- 该缺口不阻止方案设计，但会阻止最终规则实现。

### Build Readiness

在开始编码前必须满足：

- 至少定义 `support/interview/survey` 的来源规则。
- 明确多主题是否允许，以及主主题如何兼容旧字段。
- 明确重复反馈是否全部进入证据。
- 明确无链接时的证据展示方式。
- 准备按来源覆盖正常、冲突、空匹配、重复、缺失证据的样例。

### 功能验收

- 同一文本在不同来源下可产生不同主题或紧急程度。
- `--source` 仍可用，且只影响输入范围，不破坏来源规则。
- CSV 与 JSON 均能读取相同语义字段。
- 每个输出项都能追溯到原始反馈 ID和原文。
- 去重后所有原始重复项仍可从证据集合追溯。
- 多主题反馈不会被静默丢弃。
- 未配置来源使用默认规则并明确标识。
- JSON 与 Markdown 都包含来源、主题、紧急程度和证据引用。
- 旧版单主题字段或其兼容策略有明确说明。

### 质量验收

建立按来源切片的最小回归集，至少覆盖：

- 来源相同、文本相同；
- 来源不同、文本相同；
- 多主题命中；
- 高紧急与普通紧急；
- 未知来源；
- 缺少证据 URL；
- CSV/JSON 等价输入；
- 重复项证据完整保留。

阈值应由业务 owner 在规则表确认后设定；当前材料不足以合理指定准确率数字。

## 6. 仍需人类 owner 确认

1. 各反馈来源分别关注哪些主题。
2. 哪些来源下的词或场景应判为高紧急。
3. 是否允许一条反馈拥有多个主题。
4. 旧版 `theme` 字段是保留主主题，还是升级为数组并接受格式变更。
5. “证据引用”需要 ID、原文、URL、系统记录位置，还是全部保留。
6. 重复反馈是否应影响主题数量、紧急程度统计或仅作为证据。
7. 无证据链接时，是否接受 ID+原文作为最低可追溯形式。

当前结论：可以按“确定性、来源感知、证据不丢失、格式兼容”的方向实施；在 owner 确认上述规则前，不应开始正式编码。
