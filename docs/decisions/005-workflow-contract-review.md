# 工作流合同与可复用性审查

状态：已实施（2026-09-11）。

## 审查结论

当前 Skill 覆盖从机会/任务资格判断到认知、产品定义、方案、实现、验证、发布和复盘的完整产品交付闭环，并通过 Profile、Planner、Context、Executor、Registry、Replan 支持按范围执行和跨会话继续。它可以作为 AI 产品经理的本地执行 Skill 频繁复用。

“完整”限定为一个 AI 产品从任务进入到交付完成的工作流。组织设计、产品组合管理、年度经营计划、完整财务建模、法务采购、销售运营和多人实时协同不是默认节点；只有当前产品明确需要时才作为范围内任务或外部项目要求处理。这个边界避免把 Skill 变成通用企业管理手册。

## 审查前的主要缺口

| 维度 | 发现 | 影响 | 本次处理 |
|---|---|---|---|
| 工作流覆盖 | 八节点齐全，没有缺失的顶层交付阶段 | 无需增加节点 | 保持八节点不变，明确覆盖边界 |
| 节点输入 | 7 个节点使用“原文未单列固定输入”占位 | Agent 无法稳定判断何时可开始 | 为八节点补充最小必要输入 |
| 节点过程 | 多个节点只有能力词或一句原则 | 执行顺序依赖临场发挥 | 增加 4–5 步的最小工作过程 |
| 节点输出 | 多个节点只引用 Task expected_output | 产物不易复用和验收 | 定义节点级最低输出内容，不增加固定模板 |
| 节点完成 | 多个节点只链接全局 Completion Criteria | 容易把“做过”误认为“完成” | 增加节点级成功判断，继续受全局完成条件约束 |
| 边界 | Do Not 多为相同通用句 | 难以阻止节点越权和过度工作 | 增加每节点特有边界 |
| README | 面向维护者，安装、调用、恢复和示例分散 | 新用户难以上手 | 重写为从安装到维护的使用说明书 |
| 标准化 | 结构验证只检查标题存在 | 占位内容仍可通过 | 增加合同非空与禁用占位检查 |

## 节点合同标准

每个 lifecycle reference 必须回答：

1. **Purpose**：本节点解决什么决策或交付问题；
2. **Activation Conditions**：何时加载并执行；
3. **Required Inputs**：可靠开始所需的最小信息或资产；
4. **Procedure**：完成节点所需的最小步骤；
5. **Outputs**：需要交付或供后续复用的结果；
6. **Completion Criteria**：什么证据说明节点已经完成；
7. **Dependencies / Load With**：依赖和按需读取范围；
8. **Do Not**：本节点不得越过的边界。

Capability 仍是能力，不自动成为任务；节点输出描述最低信息内容，不强制统一文档模板。具体任务继续由 Planner 根据缺口产生，避免标准化演变为机械瀑布流程。

## 干净度与复杂度判断

- Kernel 继续只保存核心原则、路由、全局约束和完整闭环。
- 节点详细规则只在对应 lifecycle canonical location 维护。
- README 只解释如何使用并链接 canonical rules，不成为第二份 SOP。
- 不新增 lifecycle node、runtime capability、Gate、schema、Agent 层或基础设施。
- 不把竞品分析、路线图、商业化、增长、合规等能力设为每个项目必做；它们由目标、范围、风险或依赖触发。

## 验收要求

- 八节点、六项 Runtime capability、三项 Gate 和现有枚举保持不变；
- 所有 lifecycle contract section 非空且不含“原文未定义”占位；
- 内部链接与 canonical locations 有效；
- P1/P2/P3 自动化测试通过；
- Skill 内容变化后，Routing 与 Phase 2 Behavior 使用新目录和真实工具 trace 重跑；
- README 可独立支持安装、首次调用、单次任务、持续项目、恢复、变更和维护验证。
